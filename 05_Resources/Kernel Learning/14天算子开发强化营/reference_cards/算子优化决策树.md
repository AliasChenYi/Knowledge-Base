# 算子优化决策树

拿到一个慢算子，按这个顺序判断。

## 1. 它真的是热点吗？

不是热点：

```text
先不要优化。
```

是热点：

```text
继续。
```

## 2. 正确性 reference 有吗？

没有：

```text
先写 reference 和 tests。
```

有：

```text
继续。
```

## 3. Baseline 明确吗？

没有：

```text
先确定 baseline：旧实现、PyTorch、vendor library、编译器。
```

有：

```text
继续。
```

## 4. 更像哪种瓶颈？

### Launch-bound

现象：

- 很多小 kernel。
- 单个 kernel 很短。
- timeline 中空洞多。

方向：

- fusion。
- torch.compile。
- Triton fused kernel。

### Memory-bound

现象：

- 算术强度低。
- memory throughput 高。
- compute utilization 低。

方向：

- 减少 HBM 读写。
- coalescing。
- vectorized load/store。
- shared memory tile。
- layout 调整。

### Compute-bound

现象：

- compute utilization 高。
- memory throughput 不高。
- 大 GEMM/conv 常见。

方向：

- Tensor Core/MMA。
- tiling。
- pipeline。
- instruction-level 优化。

## 5. 是否已有成熟库

有：

```text
优先考虑 cuBLAS/cuDNN/CUTLASS/oneDNN/vendor library。
```

没有或需要特殊融合：

```text
考虑 Triton/CUDA/custom backend。
```

## 6. 是否值得维护

如果收益小、shape 少、代码复杂、风险高：

```text
谨慎合入。
```

如果收益稳定、shape 重要、测试完整：

```text
推进合入。
```
