# 算子任务拆解手册

## 1. 拿到任务后先别写代码

真实工作里，mentor 可能会说：

```text
你看一下这个 RMSNorm 算子，能不能优化一下？
```

新人最容易马上去写 kernel。更稳的做法是先拆任务。

## 2. 第一轮必须问清的 10 个问题

1. 这个算子的数学语义是什么？
2. 输入输出 shape 是固定的还是动态的？
3. 支持哪些 dtype？
4. 支持哪些 layout/stride？
5. 是否要求支持 non-contiguous？
6. correctness reference 是什么？
7. 误差标准是什么？
8. benchmark shape 列表在哪里？
9. 当前 baseline 是谁？
10. 目标是 latency、throughput、带宽、功耗，还是端到端收益？

## 4. 推荐执行顺序

### 第 1 步：复现 baseline

你先要能跑出和别人一样的 baseline。

输出：

```text
baseline command
baseline result
环境版本
```

### 第 2 步：建立 reference

reference 可以是：

- PyTorch 实现。
- CPU C++ 实现。
- vendor library。
- 团队已有正确实现。

输出：

```text
correctness test
误差标准
随机测试
边界测试
```

### 第 3 步：初步 profiling

先判断：

- memory-bound？
- compute-bound？
- launch-bound？
- layout conversion？
- 通信等待？

输出：

```text
profiling 证据截图或文字摘要
瓶颈猜测
```

### 第 4 步：提出方案

方案不要一上来太大。先做低风险版本：

- 调参数。
- 改访问模式。
- fusion。
- 特定 shape 专门优化。
- 调用更合适的库。

### 第 5 步：实现与验证

每次改动都要跑：

- correctness。
- benchmark。
- 必要时 profiling。

### 第 6 步：汇报

汇报不是“我改了代码”，而是：

```text
我确认了什么问题，做了什么优化，在哪些 shape 有收益，哪些 shape 没收益，风险是什么，下一步是什么。
```

## 5. 判断是否值得优化

如果一个算子：

- 不是热点。
- baseline 已经非常强。
- shape 很少出现。
- 优化维护成本很高。
- correctness 风险很大。

那可能不值得手写 kernel。

成熟工程师不是所有东西都手写，而是知道什么时候不要手写。

## 6. 一句话工作流

```text
语义确认 -> baseline 复现 -> reference 测试 -> profiling 定位 -> 小步优化 -> 数据汇报 -> 明确风险
```
